# Personal Team installation and possible AltStore migration

Reviewed 2026-09-30. Read-only documentation/source investigation; no account login, registration, certificate/profile creation, installation, credential access, or migration was performed for this review.

## Current installation decision

Keep the project's application identifier **`com.cmkang131.companion`** fixed. Install first through Xcode Personal Team, then update through that same Xcode signing path. Keep the selected Team and resulting App ID prefix stable. Do not uninstall the existing app merely to resolve an update failure.

AltStore Classic automatic refreshing is a separate future decision. It is not yet verified as an in-place update path for this Xcode-installed app.

## Seven-day limit and refreshing

Apple permits on-device development with a free Personal Team after signing into Xcode. Its current account guide specifies 10 App IDs, 3 devices, and 3 apps per device; Personal Team provisioning profiles expire **7 days from issuance**, requiring reprovisioning/rebuild and reinstall. It is not seven days from the first launch. [Apple account guide](https://developer.apple.com/help/account/basics/about-your-developer-account)

AltStore Classic also documents seven-day app expiration. It attempts background refresh and offers manual refresh. It needs a running AltServer reachable on the same Wi-Fi network or through USB. Background refresh is an attempt, not an assurance that every device refreshes before expiry. AltStore therefore automates periodic re-signing rather than removing the free-account expiration. [AltStore Getting Started](https://faq.altstore.io/altstore-classic/your-altstore), [AltServer](https://faq.altstore.io/altstore-classic/altserver)

## Why the same Apple account is not enough for migration

The official AltStore source was inspected at commit `56854e66fef2eac32dad88dcbad1dc131d430e60` (the repository's `marketplace` branch at inspection). These are source-level findings, not a claim that a particular installed AltStore binary was tested:

- `FetchProvisioningProfilesOperation` looks for an **AltStore database record** with the original bundle ID. If it was installed with the same team, AltStore reuses that record's resigned bundle ID.
- Otherwise, an ordinary app's ID is generated by appending `.` and the signing team ID to its original bundle ID. AltStore itself has a different legacy naming branch. An existing installation associated with a different team also takes a newly generated identifier.
- `ResignAppOperation` replaces the app's `CFBundleIdentifier` with the provisioning profile's bundle identifier before signing.

Sources: [ID selection, lines 126–193](https://github.com/altstoreio/AltStore/blob/56854e66fef2eac32dad88dcbad1dc131d430e60/AltStore/Operations/FetchProvisioningProfilesOperation.swift#L126-L193), [Info.plist rewrite, lines 112–119](https://github.com/altstoreio/AltStore/blob/56854e66fef2eac32dad88dcbad1dc131d430e60/AltStore/Operations/ResignAppOperation.swift#L112-L119).

**Inference for Companion:** a first ordinary AltStore import can become `com.cmkang131.companion.<TEAM_ID>` instead of the Xcode-installed `com.cmkang131.companion`, even when both use the same Apple account. That should be treated as a different application identity, not an automatic adoption of the existing installation. The source does not establish a supported Xcode-install adoption path that preserves this project's fixed installed ID.

## What must match for an in-place update

The bundle ID identifies an app throughout the system and is used for preferences and signature validation. New iOS apps receive their own sandbox containers. A changed ID therefore cannot be assumed to inherit another app's preferences/files. [Apple CFBundleIdentifier](https://developer.apple.com/documentation/bundleresources/information-property-list/cfbundleidentifier), [Apple file-system overview](https://developer.apple.com/library/archive/documentation/FileManagement/Conceptual/FileSystemProgrammingGuide/FileSystemOverview/FileSystemOverview.html)

For development/beta upgrades, Apple documents rejection when the new `application-identifier` entitlement differs from the installed app. That identifier includes an App ID prefix as well as the bundle ID. The actual signed entitlements and provisioning profile matter; the app's name, source bundle ID, and account email alone are insufficient. Profiles must also authorize the target device and required entitlements. Apple's archived note describes exceptional prefix-migration mechanisms, but those are not an established Personal Team/AltStore migration path for this project. [Apple TN2319](https://developer.apple.com/library/archive/technotes/tn2319/_index.html)

Keychain continuity is a separate check. By default, iOS keychain access is scoped to the signed app's access groups; the application identifier provides its private group. A shared service string alone grants no cross-app access. Companion currently saves its optional gateway token through `GenericPasswordKeychainStore` without an explicit shared access group. Thus a rewritten bundle ID or changed prefix may leave the new app unable to read the previous token. [Apple keychain access groups](https://developer.apple.com/documentation/security/sharing-access-to-keychain-items-among-a-collection-of-apps), [Apple QA1726](https://developer.apple.com/library/archive/qa/qa1726/_index.html)

AltStore's documented deactivate/activate operation backs up and restores apps that it manages. That documentation does **not** establish import of an unrelated Xcode installation's sandbox or private keychain. Do not describe it as a migration guarantee. [AltStore Activating Apps](https://faq.altstore.io/altstore-classic/activating-apps)

## Future verification before switching installers

1. Record the installed app's bundle ID, signed `application-identifier`, Team/App ID prefix, relevant keychain entitlements, and profile expiry using non-secret metadata only.
2. Compare the actual candidate re-signed package before installation. If its identity changes, treat migration and data transfer as separate work; preserve the original installation.
3. Test an ordinary Xcode update using non-sensitive preferences/files and a disposable keychain marker. Check that it replaces one icon and retains each data class. This validates the tested path only.
4. If AltStore is later selected, verify its exact release and behavior, prepare a supported transfer/backup plan where necessary, and test refreshing. Saved gateway tokens may need user re-entry and device authorization may need renewal; neither is guaranteed to transfer.

No source bundle ID changes or custom re-signing workarounds are proposed. Paid membership and TestFlight enrollment are outside the approved route.
